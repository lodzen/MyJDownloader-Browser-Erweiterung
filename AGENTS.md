# AGENTS.md — MyJDownloader Browser Extension

Chrome/Edge extension for MyJDownloader (JDownloader remote). Tech: AngularJS
1.x + RequireJS/AMD + jQuery Deferred for the pages, `vendor/js/jdapi.js` for
the MyJDownloader API, vanilla-JS MV3 service worker for background logic.

## Key architecture facts

- `manifest.json` is **MV3**: `background.service_worker` =
  `scripts/background_service_worker.js`. The old Angular background page
  (`index.html` + `BackgroundCtrl`) still ships but self-disables under MV3 —
  do not re-enable it; port logic into the service worker instead.
- The MyJDownloader API client lives in **each page** (popup, toolbar iframe,
  options) via `myjdClientFactory`/`MyjdService`, not in the worker. Session
  persists through `chrome.storage.local["jdapi/src/core/core.js"]`;
  `MYJD_CONNECTION_ACTIVE` (storage) is the shared logged-in flag — treat it
  as last-known-good, never write `false` from a transient restore failure.
- DNR rules live in `rules/cnl_rules.json`. `web_accessible_resources`
  `matches` must list the *requesting page* origins, not the asset's own URL.
- `chrome.scripting.executeScript` defaults to the isolated world — use
  `world: 'MAIN'` to set page-visible globals like `window.jdownloader`.
- `jdapi.js` requests are **enqueued forever while not CONNECTED** — callers
  must guard API state or add timeouts; a jQuery deferred that never settles
  silently hangs the UI.

## Testing the extension locally

- **Branded Chrome 158 loads the extension fine** — but the `--load-extension`
  CLI flag is ignored. Either:
  - `chrome://extensions` → Developer Mode ON → **Load unpacked** (UI), or
  - CDP `Extensions.loadUnpacked` on the browser WS endpoint — the `path`
    **must use forward slashes** (`C:/Users/...`); backslashes fail with
    `File path cannot be resolved`. CDP-loaded unpacked extensions do **not**
    survive a browser restart — re-run `loadUnpacked` each session, or load
    once via the UI to persist.
- Launch a debuggable instance:
  `chrome.exe --user-data-dir=<tmp> --remote-debugging-port=9224` then load
  via CDP as above. Edge works too (same CDP surface).
- The embedded Devin/IDE browser is launched with `--disable-extensions` —
  the extension cannot load there. Drive your own instance via CDP on the
  remote-debugging port (`/json` → `webSocketDebuggerUrl` → `Runtime.evaluate`
  / `Network.enable`; attach to the extension's `service_worker` target for
  `console` logs and `chrome.storage` inspection).
- Open the popup directly at `chrome-extension://<id>/popup.html`; the
  toolbar at `chrome-extension://<id>/toolbar.html?id=<tabId>`.
- A real JDownloader listens on `127.0.0.1:9666` when running
  (`GET /jdcheck.js` → 200 is a quick health check).
- If a **store-installed copy of this extension** is also enabled (Edge sync),
  disable it during testing — both copies race to intercept `localhost:9666`.

## Conventions

- No build step — the repo *is* the unpacked extension; edit files in place.
- AngularJS 1.x (`$scope`, `$q`, `$http`) + RequireJS `define([...])` modules;
  keep new code consistent with the surrounding style.
- Service worker is plain ES2020 (no Angular/jQuery available there).
- Don't commit secrets. `chrome.storage.local` is the extension's datastore;
  `StorageService` owns the settings keys.
- `_metadata/` content is generated by the browser — do not hand-edit it.
